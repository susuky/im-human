# Scene Packs / 可直接發場景包

> 本文件是解釋、範例與操作細則；行為合約的單一來源是 `SKILL.md`，兩處表述不一致時以 `SKILL.md` 為準。

Scene Packs 是面向可發布文本的子場景策略。它不替代 [場景禁改表](./scene-guardrails.md)、[Protected Spans](./protected-spans.md) 或 `Tier` 判斷；只要文本本身像 README、release note、forum post 或 issue reply，就進一步判斷“這段應該像哪一種發布文本”。

使用順序：

1. 先判大場景：`chat / status / docs / public-writing`
2. 先劃 protected spans：版本號、路徑、鏈接、命令、引用、編號、責任歸屬都不能漂
3. 再看是否命中本文件的 scene pack
4. 最后按 scene pack 的發布目的收束語氣；如果它同時像 `docs / status`，取更保守的保真邊界

預設不要因為 scene pack 新增全局詞條。只有新樣本已經超出現有問題族，且會改變誤殺邊界時，才考慮補 `phrases` 或 `structures`。

## `README`

預設目標：

- 第一屏能讓讀者快速知道：這是什么、給誰用、解決什么問題。
- 語氣可以有個性，但不能只剩愿景、價值和姿態。

必須保留：

- 項目名、目標用戶、核心能力、支持平臺
- 命令、安裝方式、文件路徑、鏈接
- 已有 benchmark 數量、版本號和能力邊界

優先刪除：

- `AI 全面重塑開發范式`
- `面向未來`
- `深度賦能`
- `內容生產鏈路`
- `價值閉環`
- 沒有具體能力或證據支撐的 `真正能 / 做快做穩 / 更像人寫的` 等自我宣傳結果句
- 只說“先進 / 智能 / 全方位”但不說具體做什么的句子

預設力度：

- `standard`
- 如果 intro 只剩口號，可以升到 `aggressive`，但不能編造項目能力

誤殺邊界：

- README intro 允許一句有辨識度的定位句
- `CLI / API / benchmark / Codex / ChatGPT` 等項目術語應保留
- 不要把 README 改成社交媒體短帖

Before:

> 在 AI 全面重塑開發范式的今天，我們打造了一款真正面向未來的中文表達優化工具，深度賦能開發者的內容生產鏈路。

After:

> `說人話` 是一個中文優先的 rewrite skill，用來把 AI 寫出來的套話、表演感和工程師腔改回自然表達。適合 README、release note、issue 回復和日常協作文本。

## `release-note`

預設目標：

- 讓讀者快速知道這一版改了什么、怎么驗證、有沒有破壞性變化。
- 優先列表化，少寫發布宣言。

必須保留：

- 版本號、日期、文件名、配置項、issue / PR 編號
- 變更類型：新增、修復、調整、測試
- 已知限制和遷移提示

優先刪除：

- `Release Highlights` 后面只寫空泛升級
- `系統性升級`
- `全新躍遷`
- `感謝所有用戶持續支持`
- `共同見證`
- 沒有來源的性能、效率、用戶反饋數據

預設力度：

- `standard`
- 如果缺少具體 changelog，不要編造；改成提示“這里需要補具體變更”

誤殺邊界：

- release note 可以正式、簡潔、列表化
- 不要為了“像人”把 changelog 列表改成故事
- 不要刪版本號、文件路徑、case 數量和 PR / issue 編號

Before:

> 本次版本是一次面向真實場景的系統性升級，感謝所有用戶的持續支持，讓我們共同見證中文 AI 寫作體驗的全新躍遷。

After:

> - 新增 `references/scene-packs.md`，覆蓋 README、release note、forum post 和 issue reply
> - `evals/benchmark.md` 增加 8 條 scene pack 回歸用例
> - 新增 `evals/results-v1.8.0.md` 記錄本輪復核結果

## `forum-post`

預設目標：

- 像維護者在社區里講真實觀察：做了什么、發現什么、哪里還不穩、想要什么反饋。
- 允許口語，但要有具體經歷支撐。

必須保留：

- 時間、動作、具體文件、樣本數量、觀察到的問題
- 原作者真實態度和社區語氣
- 鏈接、命令、版本號和被討論詞

優先刪除：

- 公司公告腔
- `系統性重塑`
- `用戶痛點`
- `多元場景`
- `方法論閉環`
- `穩穩接住核心訴求`

預設力度：

- `standard`
- 如果帖子本來有具體經歷，只清理姿態層，不要改成正式公告

誤殺邊界：

- 具體經歷后的口語詞可以保留
- 社區帖允許“踩坑 / 折騰 / 還差一點”這類真實語氣
- 不要把個人復盤改成 README 或 release note

Before:

> 折騰這個工具一個月后，我深刻意識到，中文 AI 寫作治理不是一次簡單的詞表擴張，而是一場圍繞真實表達場景的系統性重塑。

After:

> 做這個工具一個月后，我發現光刪詞表不夠。README、release note、issue 回復和論壇帖看起來都是“公開文本”，但改法其實不一樣。

## `issue-reply`

預設目標：

- 先回答問題是否成立，再給復現狀態、判斷和下一步。
- 不做客服式安撫，不替維護者承諾未排期能力。

必須保留：

- bad case 原句、場景標簽、復現結果
- issue / PR 編號、文件路徑、規則名、benchmark 編號
- “已確認 / 未復現 / 需要更多樣本 / 會補測試”的狀態

優先刪除：

- `感謝寶貴反饋`
- `你問到了核心`
- `我們已經充分接住這個場景`
- `持續優化相關能力`
- `如果你愿意我可以繼續幫你`

預設力度：

- `minimal` 或 `standard`
- 有具體技術資訊時保守處理；沒有具體下一步時，不要編造排期

誤殺邊界：

- issue 回復可以短、硬、直接
- `bad case / docs / SNF / benchmark / repro` 是維護語境里的正常術語
- 不要把明確的維護回復改成社交式寒暄

Before:

> 感謝你非常寶貴的反饋！你這個問題問到了項目體驗的核心。我們已經充分接住了這個場景，也會在后續版本中持續優化相關能力。

After:

> 收到，這個 case 我能復現。它屬于 `docs` 場景里的誤殺，下一版先補一條 SNF；如果現有規則已經能放行，就只加回歸用例。
