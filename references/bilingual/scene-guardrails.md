# 場景禁改表

> 本文件是解釋、範例與操作細則；行為合約的單一來源是 `SKILL.md`，兩處表述不一致時以 `SKILL.md` 為準。

先判場景，再判斷哪些內容不能亂動。去模板感不等於把所有文本都改成一個口氣。

只要環境裡能讀 `references/`，預設先用 [Protected Spans](./protected-spans.md) 劃出不能漂的片段，再按這裡的場景禁改項收窄改寫範圍。

本文件只定義大場景邊界。README、release note、forum post、issue reply 這類更細的發布場景，即使初判像 `docs` 或 `status`，也要補看 [Scene Packs](./scene-packs.md)，同時保留這裡更保守的事實和術語邊界。

## `chat`

目標：

- 自然、直接、有回應感

預設檔位：

- `minimal`

無源引用預設策略：

- `rewrite-safe`

不要亂動：

- 不要為了「去 AI 味」把回覆改得更硬
- 不要憑空拔高語氣或補價值判斷
- 不要把簡單回應改成總結陳詞
- 不要替對方做心理分析、關係診斷或空泛安撫

優先保留：

- 對話節奏
- 具體回應關係
- 合理的口語停頓
- 用戶明確要求保留的原話或引用片段

## `status`

目標：

- 事實密度高，讀完知道進展、問題、下一步

預設檔位：

- `minimal` 或 `standard`

無源引用預設策略：

- `audit-only`

不要亂動：

- 不要刪時間線
- 不要刪責任歸屬
- 不要把風險說輕
- 不要為了「更像人」犧牲匯報效率

優先保留：

- 時間、動作、結果、風險、阻塞點
- 數字、日期、範圍和責任歸屬

## `docs`

目標：

- 可檢索、可重現、可引用

預設檔位：

- `minimal`

無源引用預設策略：

- `audit-only`

不要亂動：

- 不要破壞術語穩定性
- 不要改掉檢索詞、命令、介面名稱、欄位名
- 不要為了口語化犧牲系統主語和命令式說明
- 不要把正式說明改成閒聊體

優先保留：

- 術語
- 系統行為主語
- 步驟順序
- 限定條件
- 命令、路徑、參數、欄位、錯誤訊息和狀態碼

## `public-writing`

目標：

- 語域統一，有判斷但不端著

預設檔位：

- `standard`

無源引用預設策略：

- `rewrite-safe`

不要亂動：

- 不要為了節奏製造誇張判斷
- 不要把克制文風改成自媒體吆喝腔
- 不要硬造金句
- 不要把正式公告改成社媒評論

優先保留：

- 作者原有立場
- 正常的正式度
- 必要的修辭節奏
- 已有事實、歸屬和可核對引用

長文補充：

- 中文長文（約 1000 字以上）預設優先 `bounded` scope，尤其是觀點文、復盤文、評論文和帶段落節奏的公開文本：句內洗實句、整句空話進「建議刪除（待確認）」清單交用戶拍板，不併句不重排
- 用戶明確要求「完全原樣 / 一句都別刪 / 嚴格保句數」，或回饋 `bounded` 仍刪多了時，再切到更嚴格的 `in-place`（整句空話也不刪，只句內降調）
- 用戶 prompt 含 `保長度 / 別縮水 / 字數 / 節奏 / 別刪 / 盡量原樣` 這類信號時，即使原文沒到 1000 字，也按長文處理
- `bounded / in-place` 下都不把整段壓成短摘要；先保段落節奏和承擔轉場的重複，區別只在整句空話是「進刪除清單」還是「留著只做句內降調」

## 混合場景處理

如果一段文本同時命中多個場景：

1. 先判主要用途
2. 先劃 protected spans，再以主場景的禁改項為上限
3. 只清理次場景裡明顯突兀的詞，不追求絕對純化
